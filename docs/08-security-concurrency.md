# 8. Безопасность, идемпотентность, транзакции, конкурентный доступ

## 8.1 Модель конкурентного доступа

Экземпляр книги уникален, поэтому **строка `wp_book_items` — это мьютекс экземпляра**. Любая операция,
которая меняет судьбу экземпляра (резерв, удаление из корзины, checkout, webhook, снятие резервов,
синхронизация, действия администратора), берёт `SELECT … FOR UPDATE` этой строки. Все решения принимаются
только по данным, прочитанным под блокировкой.

Ограничения БД — **второй рубеж**. Если в коде появится ошибка (кто-то забудет `FOR UPDATE` или напишет
новый endpoint), инвариант всё равно не нарушится:

| Инвариант | Код (рубеж 1) | БД (рубеж 2) |
|---|---|---|
| Не более одного активного резерва на экземпляр | `FOR UPDATE` item + проверка `availability_status='available'` | `UNIQUE(active_book_item_id)`, generated `IF(status='active', book_item_id, NULL)` |
| Не более 3 попыток пользователя на экземпляр | `COUNT(*)` под блокировкой item | `UNIQUE(user_id, book_item_id, attempt_no)` + `CHECK(attempt_no BETWEEN 1 AND 3)` |
| Книга — активная позиция только одной корзины | то же | `UNIQUE(active_book_item_id)` в `wp_book_cart_items` |
| Одна открытая корзина на пользователя | `FOR UPDATE` корзины | `UNIQUE(open_cart_user_id)` |
| Одна продажа на экземпляр | `FOR UPDATE` item + проверка `checkout_pending` | `UNIQUE(book_item_id)` в `wp_book_sales` |
| Один webhook-эффект на событие | `FOR UPDATE` события | `UNIQUE(provider, provider_event_id)` |
| Один заказ на повтор checkout | поиск по `checkout_request_id` | `UNIQUE(user_id, checkout_request_id)` |
| Один `running`-прогон синхронизации | `GET_LOCK` | `UNIQUE(running_source)` |
| Один возврат на решение | статус строки возврата под `FOR UPDATE` | `UNIQUE(idempotency_key)`, `UNIQUE(provider_refund_id)` |
| Суммы положительны, коды в верхнем регистре | валидация в сервисах | `CHECK (… > 0)`, `COLLATE utf8mb4_bin` + `REGEXP '^[A-Z]{3}$'` |
| `sold` ⇔ `sold_at`, итог заказа, `paid_at` у оплаченного | код сервиса | `CHECK`-ограничения |

### Можно ли сделать уникальность активного резерва в MySQL 8?

Да. В MySQL нет частичных индексов (`WHERE status='active'`), но UNIQUE-индекс InnoDB допускает
сколько угодно `NULL`. Поэтому заводится STORED generated column, которая равна `book_item_id` у активной
строки и `NULL` у всех остальных:

```sql
active_book_item_id BIGINT UNSIGNED
  GENERATED ALWAYS AS (IF(reservation_status = 'active', book_item_id, NULL)) STORED,
UNIQUE KEY uq_reservations_one_active_per_item (active_book_item_id)
```

Альтернатива с 8.0.13 — функциональный индекс `UNIQUE ((IF(reservation_status='active', book_item_id, NULL)))`.
Он работает так же (это скрытая virtual-колонка), но хуже виден в `SHOW CREATE TABLE`, и ошибка 1062
называет функциональный индекс менее понятно. Выбрана явная STORED-колонка. Работа механизма проверена
в `tests/mysql/run.sh`: второй `INSERT` активного резерва получает `ERROR 1062`.

Почему одного индекса мало и нужен `FOR UPDATE`. Индекс защищает только таблицу резервов, а резерв меняет
четыре сущности: экземпляр, резерв, позицию корзины и корзину. Без блокировки экземпляра две транзакции
могли бы по-разному прочитать `availability_status` и попытку пользователя. Блокировка сериализует всю
операцию, а индекс страхует от ошибок в коде.

## 8.2 Транзакции в WordPress

У `$wpdb` нет API транзакций, поэтому плагин использует свой хелпер `Db::transaction()`:

```php
$result = $db->transaction(function () use ($userId, $itemId) {
    // только запросы к БД; никаких HTTP-вызовов, писем и do_action() сторонних плагинов
});
```

Что делает хелпер:

1. Соединение `$wpdb` общее с ядром и другими плагинами, поэтому хелпер **не меняет сессию насовсем**:
   - перед каждым `START TRANSACTION` выполняет `SET TRANSACTION ISOLATION LEVEL READ COMMITTED`
     (действует только на ближайшую транзакцию);
   - запоминает `@@session.time_zone` и `@@session.sql_mode`, ставит `time_zone = '+00:00'` и строгий режим
     на время транзакции и после `COMMIT`/`ROLLBACK` возвращает прежние значения. Поэтому
     `DEFAULT CURRENT_TIMESTAMP(6)` в таблицах плагина всегда в UTC, а чужой код не замечает изменений.
2. `START TRANSACTION` → вызов функции → `COMMIT`. При исключении — `ROLLBACK`.
3. При `errno 1213` (deadlock) или `1205` (lock wait timeout) повторяет транзакцию с паузой 50–200 мс
   и случайным джиттером: до 2 раз в веб-запросах (пользователь не ждёт дольше ~10 с) и до 3 раз в cron
   и WP-CLI. После исчерпания попыток — `503 uniundata_conflict_retry` с `Retry-After: 1`.
   `$wpdb` не отдаёт код ошибки, поэтому он берётся через `mysqli_errno($wpdb->dbh)`.
4. Вложенный вызов `transaction()` присоединяется к внешней транзакции (счётчик глубины, без SAVEPOINT).
   `COMMIT`, `ROLLBACK` и повторы выполняет только внешний уровень, `maxRetries` вложенного вызова игнорируется.
   Если вложенная функция бросила исключение, транзакция помечается rollback-only: даже если вызывающий код
   перехватил исключение, внешний уровень не сделает `COMMIT`. После `1213`/`1205` любой следующий запрос через
   `Db` в этой попытке бросает исключение, и транзакция повторяется целиком. Если на соединении уже открыта
   чужая транзакция, `SET TRANSACTION` даёт ошибку 1568, и `Db` бросает исключение, а не фиксирует чужую работу.
   Сервисы плагина транзакции не вкладывают: каждая публичная операция — одна транзакция.
5. Все записи плагина в БД идут через этот хелпер, никаких «сырых» `$wpdb->insert()` вне транзакции.

Почему **READ COMMITTED**, а не REPEATABLE READ по умолчанию:

- в RR первый обычный `SELECT` фиксирует снимок, и последующие обычные `SELECT` в той же транзакции видят
  устаревшие данные. Легко принять решение по снимку, хотя блокировку взяли позже;
- в RC почти нет gap-локов на вставках, поэтому меньше deadlock-ов между резервами по соседним `id`;
- корректность обеспечивают блокирующие чтения (`FOR UPDATE`), а не уровень изоляции.

Правила, которые соблюдаются во всём коде:

- `SELECT … FOR UPDATE` строки экземпляра перед любым решением о его статусе;
- переход статуса — условный `UPDATE … WHERE id = %d AND availability_status = 'reserved'` с проверкой
  `$wpdb->rows_affected === 1`. Если строка не обновилась, это ошибка логики: откат и исключение;
- HTTP-вызовы банка и источника каталога **никогда** не выполняются внутри транзакции (иначе блокировки
  держатся секунды);
- email, PDF, возвраты и уведомления запускаются **после** `COMMIT` через Action Scheduler с идемпотентными
  аргументами (`order_id`, `event`). Если транзакция откатилась, письма не будет;
- `innodb_lock_wait_timeout` для транзакций плагина — 5 с: значение сохраняется, выставляется и
  восстанавливается вместе с `time_zone` и `sql_mode`, поэтому другие плагины на общем соединении
  сохраняют свои 50 с. Пользователь не ждёт блокировку дольше нескольких секунд.

### Глобальный порядок блокировок

Классический deadlock возникает, когда две транзакции берут блокировки в разном порядке. Поэтому все
операции берут их в одном и том же порядке (операция может пропускать уровни, но не менять их порядок):

```
0. wp_book_sync_runs, wp_book_records   (только синхронизация; см. правило ниже)
1. wp_book_carts          (открытая корзина пользователя)
2. wp_book_items          (по возрастанию id)
3. wp_book_reservations
4. wp_book_cart_items
5. wp_book_orders
6. wp_book_payments
7. wp_book_payment_events
8. wp_book_refunds
```

Два уточнения, найденные тестами на MySQL 8.0.46:

- **Записи каталога.** `INSERT` в `order_items` (checkout) и `sales` (webhook) ставит неявную S-блокировку
  на родительскую строку `wp_book_records` (проверка FK) уже после блокировки экземпляров. Поэтому
  синхронизация **никогда не держит блокировки записи и её экземпляров в одной транзакции**: сначала
  отдельная транзакция по записям пакета, затем отдельная — по экземплярам. Тогда никто не держит X на записи,
  ожидая экземпляр, и цикла нет.
- **Gap-блокировки на UNIQUE по generated column.** Если в одну и ту же миллисекунду checkout закрывает
  корзину пользователя, а другой запрос этого же пользователя создаёт новую, InnoDB проверяет дубликат
  по ещё не вычищенной (delete-marked) записи индекса `uq_carts_one_open_per_user` и ставит gap-блокировку
  даже в READ COMMITTED. Под стресс-тестом (десятки пар одновременно) это давало редкий `1213`. Инварианты
  при этом не нарушаются: транзакция откатывается целиком, и хелпер её повторяет. Поведение принято
  осознанно и зафиксировано тестом S8.7e. Альтернатива — отдельная таблица-«слот» корзины с PRIMARY KEY
  по `user_id` — убирает эффект, но усложняет схему ради крайне редкого случая.

Если операция знает только «нижний» объект (webhook знает платёж, expiry знает резерв), она сначала
обычным `SELECT` определяет ID верхних объектов, затем блокирует их в этом порядке и **перепроверяет**
состояние после блокировки: за время между чтением и блокировкой всё могло измениться.

| Операция | Что блокирует (по порядку) |
|---|---|
| reserve | cart → item → (вставка reservation, cart_item) |
| remove-item | cart → item → reservation → cart_item |
| admin release | cart → item → reservation → cart_item |
| expire reservations (pass A) | cart → item → reservation → cart_item |
| checkout | cart → items (по возрастанию id) → reservations → cart_items → (вставка order/payment) |
| pay (повторная попытка) | items → order → payments |
| cancel order | items → order → payments |
| webhook / applyProviderResult | items (по возрастанию id) → order → payments → payment_event |
| expire orders (pass B) | items → order → payments |
| sync (пакет записей) | sync_run → records (по возрастанию id) — отдельная транзакция |
| sync (пакет экземпляров) | sync_run → items (по возрастанию id) — отдельная транзакция |
| webhook: продажа | items → order → payments → payment_event; INSERT `sales` — после блокировки заказа |
| возврат: решение | items → order → payments → (INSERT refund `requested`) — в транзакции решения |
| возврат: исполнение (`processRefund`) | Tx1: order → payments → refund; HTTP-вызов банка — вне транзакции; Tx2: order → payments → refund (+ `sales.refunded_at`) |

## 8.3 Матрица гонок

| Пересечение | Что может пойти не так | Защита | Итог |
|---|---|---|---|
| Два пользователя одновременно жмут «Отложить» | Оба видят `available` | Второй ждёт `FOR UPDATE` item и после первого `COMMIT` читает `reserved` | Один получает 201, второй — 409 `uniundata_item_unavailable` |
| Пользователь жмёт «Отложить» дважды (двойной клик, две вкладки) | Две попытки | `FOR UPDATE` корзины и item, проверка «у пользователя уже есть active резерв» | Второй запрос получает 200 с тем же резервом, попытка не тратится |
| Снятие истёкшего резерва ↔ checkout | Cron освобождает книгу, которую в ту же секунду оплачивают | Оба берут cart → item. Кто второй, перепроверяет: cron видит `converted_to_order` и пропускает; checkout видит `expired` и отвечает 409 `uniundata_cart_changed` | Ровно один исход, без «оплаты свободной книги» |
| Снятие истёкшего резерва ↔ резерв другим пользователем | Другой пользователь резервирует до освобождения | Другой видит `reserved` до `COMMIT` cron-а и получает 409. После `COMMIT` книга `available`, и следующий запрос проходит | Книга не бывает в двух резервах |
| Удаление из корзины ↔ checkout | Пользователь удаляет книгу, пока создаётся заказ | Обе операции начинаются с `FOR UPDATE` корзины | Либо книга в заказе (удаление получает 409), либо удалена (checkout получает 409 `cart_changed`) |
| Webhook ↔ снятие просроченных заказов (pass B) | Cron освобождает экземпляр, а банк в ту же секунду подтверждает оплату | Pass B **до** транзакции спрашивает статус платежа у банка. Обе стороны блокируют items → order. Кто второй, перепроверяет статус заказа | Webhook первый: заказ `paid`, cron видит `paid` и ничего не делает. Cron первый: заказ `payment_expired`, webhook идёт по ветке «поздний платёж» |
| Поздний успешный webhook после освобождения | Книгу уже зарезервировал другой | Ветка «поздний платёж»: если экземпляр свободен — забрать и продать; иначе `paid` + `needs_attention = late_payment_conflict` + задача возврата | Деньги не теряются, дубль продажи невозможен (`UNIQUE` в sales) |
| Повторный / параллельный webhook | Двойная продажа, двойное письмо | `UNIQUE(provider, provider_event_id)`, `FOR UPDATE` события и заказа, статус `processed`, `UNIQUE(book_item_id)` в sales | Второй вызов — no-op с ответом 200 |
| Два разных события об успехе одного платежа | Разные `event_id` | Заказ уже `paid` с этим платежом, и переход не выполняется | 200, no-op |
| Два успешных платежа одного заказа (две вкладки) | Двойное списание | Второй: `payment.succeeded`, `needs_attention = duplicate_payment`, задача возврата | Клиенту возвращается лишний платёж |
| Синхронизация ↔ резерв / оплата | Импорт перетирает `reserved`/`sold` на `available` | Sync блокирует item и **никогда** не меняет `reserved/checkout_pending/sold/blocked`. Меняется только `source_status`, и растёт `items_conflicts` | Локальный статус всегда главнее |
| Синхронизация ↔ синхронизация | Двойной импорт, двойные счётчики | `GET_LOCK(Db::lockName('sync_<source>'))` + `UNIQUE(running_source)` | Второй запуск сразу завершается |
| Источник «потерял» половину каталога | Массовое `sync_missing` | Порог безопасности: если пропало больше 10 % активных экземпляров, пометка не выполняется, прогон получает `partial`, отправляется алерт | Каталог не «обнуляется» из-за сбоя источника |
| Checkout ↔ checkout (двойной клик) | Два заказа | `FOR UPDATE` корзины + `Idempotency-Key` → `UNIQUE(user_id, checkout_request_id)` | Второй запрос возвращает тот же заказ |
| Миграция ↔ трафик | Запросы к недостроенной схеме | `GET_LOCK(Db::lockName('migrate'))`, миграции только аддитивные, обновление версии в конце | Старый код работает со старыми колонками |

## 8.4 Идемпотентность

| Операция | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /cart/reserve` | (user, item, active) | 200 с существующим активным резервом |
| `POST /cart/remove-item` | статус позиции | 200, если позиция уже `removed/expired` |
| `POST /checkout` | заголовок `Idempotency-Key` → `orders.checkout_request_id` | тот же заказ, те же суммы |
| создание платёжной сессии | `payments.idempotency_key` (UUID) передаётся банку | банк возвращает ту же сессию |
| webhook | `(provider, provider_event_id)` | 200, без изменений |
| `applyProviderResult` | статус заказа и платежа под `FOR UPDATE` | no-op, если уже применено |
| expiry | условные `UPDATE … WHERE status = 'active' AND expires_at <= now` | повторный запуск ничего не меняет |
| возврат денег | `wp_book_refunds.idempotency_key` (UUID) передаётся банку; строка `requested` создаётся в той же транзакции, где принято решение | повторный запуск задачи видит статус `pending/succeeded` и не обращается к банку повторно |
| sync | checksum + `last_seen_sync_run_id` + `source_cursor` | повторный импорт того же пакета ничего не меняет |
| письма и документы после оплаты | Action Scheduler action с args `{order_id, kind}` + отметка в аудите | обработчик проверяет, не отправлено ли уже |

## 8.5 Безопасность WordPress

**Аутентификация и права**

- Браузерные запросы: cookie-аутентификация + заголовок `X-WP-Nonce` (`wp_create_nonce('wp_rest')`).
  Без валидного nonce WordPress считает REST-запрос анонимным, и `permission_callback` возвращает 401.
  Это защищает от CSRF.
- `permission_callback` есть у каждого маршрута. Для пользовательских маршрутов он проверяет
  `is_user_logged_in()` и `current_user_can('reserve_books' | 'create_book_orders' | …)`. `'__return_true'`
  используется только для публичного каталога. У webhook банка `permission_callback` — `permitWebhook`:
  дешёвые транспортные проверки (необязательный IP allowlist, лимит отклонённых доставок). Подпись проверяется
  в callback, потому что `verifyWebhook()` одновременно проверяет и разбирает событие.
- ID пользователя берётся **только** из `get_current_user_id()`, никогда из параметров запроса.
- Доступ к заказу: мета-capability `view_book_order` через `map_meta_cap` (владелец или менеджер).
  На чужой заказ ответ 404, а не 403, чтобы не раскрывать существование.
- `public_order_id` = `uniundata_` + UUID v4 (122 бита случайности, `wp_generate_uuid4()`).
  Последовательный `id` наружу не выдаётся.

**Ввод и вывод**

- Все SQL-запросы собираются через `$wpdb->prepare()`, для `IN (…)` плейсхолдеры генерируются
  (`implode(',', array_fill(0, count($ids), '%d'))`). Конкатенации пользовательских данных в SQL нет.
- Параметры REST описываются через `args` (`type`, `enum`, `minimum`, `format`, `sanitize_callback`,
  `validate_callback`). Адреса проверяются по белому списку полей и длин и сохраняются как JSON через `wp_json_encode`.
- Вывод в шаблонах экранируется: `esc_html`, `esc_attr`, `esc_url`. Данные MARC 21 приходят из внешнего
  источника и считаются недоверенными: описание (`520`) выводится через `wp_kses_post` или как текст.
- MARCXML разбирается с `LIBXML_NONET` и без подстановки сущностей (защита от XXE), с лимитом размера записи.

**Webhook банка**

- Подпись проверяется по сырому телу (`$request->get_body()`) через `hash_hmac('sha256', …)` +
  `hash_equals()` или RSA/ECDSA-подпись провайдера. Проверяется допустимое расхождение timestamp (±5 мин) —
  защита от replay.
- Строка в `wp_book_payment_events` создаётся **только после** успешной проверки подписи. Иначе атакующий
  мог бы заранее «занять» `provider_event_id` настоящего события, и оно было бы отброшено как дубль.
  Отклонённые запросы пишутся в аудит не чаще раза в минуту (проверка по самому журналу, работает без
  объектного кэша). Лимит отклонённых доставок — 20 в минуту на IP (транзиенты) в `PaymentWebhookController`.
- Сумма, валюта и `public_order_id` из события сверяются с заказом. Если провайдер поддерживает,
  статус дополнительно запрашивается server-to-server (`fetchPayment`).
- Nonce к банку неприменим: банк не знает WordPress-сессии. Аутентичность webhook обеспечивает подпись.
- На уровне веб-сервера можно добавить IP allowlist или mTLS для `/wp-json/uniundata/v1/payment/webhook`.

**Секреты и персональные данные**

- Ключи банка и источника — в `wp-config.php` (константы) или переменных окружения, **не** в `wp_options`:
  options попадают в бэкапы, экспорт и видны плагинам и администраторам.
- В логах и `payload_redacted` нет PAN, CVV, токенов, секретов, полных адресов и телефонов. Из данных карты
  хранятся только `card_brand` и `card_last4` (разрешено PCI DSS).
- Минимизация PII: заказ хранит только данные, нужные для исполнения и бухгалтерии. IP в согласиях
  хранится как `VARBINARY(16)` и обнуляется по истечении срока хранения.
- Rate limit: `reserve` — 20 в минуту на пользователя, `checkout` — 5 в минуту, webhook — по IP.
  Реализация на транзиентах (работает и без постоянного объектного кэша).
- Злоупотребление резервами: не больше `uniundata_max_active_reservations` (по умолчанию 10) активных резервов
  у одного пользователя одновременно. Проверка выполняется под блокировкой его корзины, превышение даёт
  409 `uniundata_active_reservation_limit`. Иначе один аккаунт мог бы на час «заморозить» весь каталог.

## 8.6 Время

- В БД всё хранится в UTC (`DATETIME(6)`). Соединение плагина выполняет `SET time_zone = '+00:00'`,
  в SQL используется `UTC_TIMESTAMP(6)`. Даже если сервер MySQL настроен на локальную зону,
  `DEFAULT CURRENT_TIMESTAMP(6)` будет в UTC.
- Сравнение сроков (`expires_at <= UTC_TIMESTAMP(6)`) выполняется **в БД**, а не в PHP: так нет расхождения
  часов между веб-серверами.
- В API время отдаётся в ISO 8601 с `Z`. Таймер в корзине считается от `expires_at` с сервера, а
  `seconds_left` — подсказка для UI, не источник истины.
