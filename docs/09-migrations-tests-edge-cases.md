# 9. Миграции, тесты, edge cases

## 9.1 Миграции

### Почему не `dbDelta()`

`dbDelta()` разбирает `CREATE TABLE` регулярными выражениями и не поддерживает:

- generated columns (`GENERATED ALWAYS AS (...) STORED`), на которых держится уникальность «только активных»;
- `CHECK`-ограничения;
- `FOREIGN KEY` — при каждом запуске он пытается «привести» таблицу к описанию и выдаёт ошибки или
  лишние `ALTER`;
- осмысленные переименования и преобразования данных.

Поэтому в плагине свой версионный мигратор `src/Install/Migrator.php`:

```
option uniundata_db_version = 3          ← текущая версия схемы на сайте
Migrator::MIGRATIONS = [
  1 => 'm001_initial_schema',            ← CREATE TABLE из sql/schema.sql
  2 => 'm002_…',
  3 => 'm003_…',
]
```

Правила:

1. Мигратор запускается в `register_activation_hook` и на `plugins_loaded` (дешёвая проверка
   `get_option('uniundata_db_version') < self::VERSION`). Перед запуском берётся
   `GET_LOCK('uniundata_migrate', 30)`, чтобы при одновременных запросах после деплоя миграцию выполнил
   один процесс.
2. Версия записывается **после каждой** успешной миграции. DDL в MySQL делает неявный `COMMIT`, поэтому
   миграция пишется так, чтобы её повторный запуск после частичного сбоя был безопасным:
   `CREATE TABLE IF NOT EXISTS`, проверка `information_schema` перед `ALTER`.
3. Перед запуском проверяется окружение: `VERSION() >= 8.0.16` (нужны CHECK) и движок InnoDB.
   Иначе плагин не активируется и показывает admin notice.
4. Префикс `wp_` в SQL заменяется на `$wpdb->prefix`, кодировка — `$wpdb->get_charset_collate()`
   (если в БД `utf8mb4`).
5. Миграции на живом сайте — **expand → migrate → contract**:
   - expand: добавить колонку или таблицу (nullable / с default). Для MySQL 8 это обычно
     `ALGORITHM=INSTANT` или `INPLACE` без блокировки таблицы;
   - migrate: заполнить данные пакетами через Action Scheduler;
   - contract: убрать старое в **следующем** релизе, когда старый код уже не работает.
6. Добавление нового статуса — `ALTER TABLE … DROP CHECK …, ADD CONSTRAINT … CHECK (…)`, без
   пересоздания таблицы. Удаление статуса — только после миграции данных.
7. Деинсталляция (`uninstall.php`) **не** удаляет таблицы заказов, продаж и платежей: это бухгалтерские
   данные. Удаление — только явной WP-CLI командой с подтверждением.

### Порядок первого развёртывания

1. Staging: импорт продакшен-дампа WordPress, активация плагина, проверка `SHOW CREATE TABLE` для всех таблиц.
2. Первая синхронизация каталога через WP-CLI (`wp uniundata sync run`) с контролем счётчиков в `wp_book_sync_runs`.
3. Настройка системного cron:
   ```
   define('DISABLE_WP_CRON', true);                        # в wp-config.php
   * * * * * cd /var/www/site && wp action-scheduler run --group=uniundata --quiet
   ```
4. Проверка ролей (`wp role list`, `wp cap list book_customer`).
5. Тестовые платежи в sandbox банка: успешный, отклонённый, двойной webhook, поздний webhook.

## 9.2 Стратегия тестов

| Уровень | Что проверяем | Инструмент |
|---|---|---|
| Схема | Все CHECK / UNIQUE / FK срабатывают; generated columns; индексы используются (`EXPLAIN`) | `tests/mysql/run.sh` на MySQL 8.0 |
| Конкурентность | 7 сценариев из ТЗ + двойное создание корзины + reserve ↔ checkout одного пользователя | `tests/mysql/run.sh` (параллельные сессии, синхронизация `GET_LOCK` / `SLEEP`) |
| Unit (PHP) | `MarcExtractor` (ISBN-10→13, `title_sort` по ind2, год из 264/260/008), вычисление сумм, маппинг ошибок 1062 / 3819 → `DomainError` | PHPUnit без WordPress |
| Интеграционные (WP) | Сервисы на настоящей БД: reserve / remove / checkout / webhook / expiry / sync; права и nonce в REST | `wp-env` или `WP_UnitTestCase` (`wp scaffold plugin-tests`) с MySQL 8 |
| Контракт банка | Подпись webhook (валидная, неверная, просроченный timestamp), сверка суммы, повтор, неизвестный платёж | Записанные фикстуры sandbox + PHPUnit |
| Нагрузка | 200 параллельных «Отложить» на 1 экземпляр, 50 на разные экземпляры; deadlock-и и p95 времени ответа | k6 / wrk против staging, мониторинг `SHOW ENGINE INNODB STATUS` |
| Регрессия инвариантов | Запросы проверки инвариантов из `sql/queries.sql` должны возвращать 0 строк | Ежедневная задача + алерт |

Ключевые проверки интеграционных тестов:

- гость получает 401 на `/cart/reserve`; без `X-WP-Nonce` — тоже 401 (cookie-auth без nonce = анонимный запрос);
- пользователь без `reserve_books` получает 403;
- чужой `public_order_id` возвращает 404;
- `expected_total_amount` не совпадает с суммой корзины → 409 `uniundata_cart_changed`, заказ не создан;
- повтор `POST /checkout` с тем же `Idempotency-Key` возвращает тот же `public_order_id`;
- webhook с неверной подписью получает 401, и в `wp_book_payment_events` строки нет;
- webhook с суммой, отличной от заказа, не продаёт экземпляр, а ставит `needs_attention = amount_mismatch`.

## 9.3 Edge cases

| Ситуация | Поведение |
|---|---|
| Пользователь начал оплату на 59-й минуте резерва | Checkout разрешён (резерв активен). Дальше срок задаёт `payment_due_at` = сейчас + 30 мин + 10 мин grace |
| Пользователь вернулся с банка раньше webhook | Return-страница показывает «Платёж обрабатывается» и опрашивает `GET /orders/{id}`. Return URL оплату не подтверждает |
| Webhook так и не пришёл | Pass B после `payment_due_at` спрашивает банк (`fetchPayment`): успех → оплата, `processing` → однократное продление, иначе `payment_expired` |
| Банк подтвердил оплату после `payment_expired`, книга свободна | Экземпляр забирается обратно, заказ `paid`, продажа создаётся |
| Банк подтвердил оплату после `payment_expired`, книгу уже купил или зарезервировал другой | Заказ `paid` + `needs_attention = late_payment_conflict`, продажа только по свободным экземплярам, задача возврата по остальным, письмо клиенту |
| Сумма в webhook отличается от заказа | Продажи нет, `needs_attention = amount_mismatch`, событие `failed`, ручной разбор |
| Два успешных платежа по одному заказу | Второй — `needs_attention = duplicate_payment`, автоматический возврат |
| Пользователь удалил книгу, а потом снова нажал «Отложить» | Новая попытка (`attempt_no + 1`) в той же корзине: старая позиция уже не `active`, поэтому UNIQUE не мешает |
| Три попытки исчерпаны | 409 `uniundata_reservation_limit_reached`, кнопка у этого пользователя для этого экземпляра неактивна («Лимит резервов исчерпан»), у других пользователей — обычная |
| Администратор снял резерв | `released_by_admin`, `attempt_no = NULL`, попытка пользователю возвращается |
| Администратор блокирует экземпляр в корзине пользователя | Сначала admin release (резерв снимается), затем `blocked` — одной транзакцией |
| Цена в каталоге изменилась после резерва | Пользователь платит цену из `cart_items.unit_price_amount` (снимок). В корзине показывается пометка «цена в каталоге изменилась» |
| Источник прислал проданную книгу как доступную | `sold` не меняется, `items_conflicts++`, в аудит `sync.conflict_sold` |
| Источник перестал присылать экземпляр, который сейчас в корзине | `source_status = missing`, статус `reserved` не трогается. При освобождении экземпляр получает `sync_missing`, а не `available` |
| Источник вернул ранее пропавший экземпляр | `sync_missing → available` |
| Синхронизация упала на середине | Прогон остаётся `running` без heartbeat. Следующий запуск через 15 мин помечает его `aborted` и продолжает с `source_cursor`. Пакеты идемпотентны (checksum) |
| Источник вернул пустой или сильно урезанный список | Порог 10 %: пометка `sync_missing` не выполняется, прогон `partial`, алерт |
| MySQL перезапустился посреди транзакции | InnoDB откатывает незавершённую транзакцию, повтор запроса безопасен (идемпотентность) |
| Deadlock | Хелпер повторяет транзакцию до 3 раз, затем 503 `uniundata_conflict_retry` |
| Пользователя удаляют из WordPress | Если есть заказы — удаление блокируется (хук `delete_user`) или выполняется с анонимизацией PII в заказах. Записи заказов и продаж остаются |
| Запрос на удаление персональных данных (GDPR) | Eraser анонимизирует профиль и снимки в заказах **после** истечения сроков хранения бухгалтерских документов, до этого — только профиль и согласия на маркетинг |
| Часы веб-сервера и БД расходятся | Все сравнения сроков выполняются в SQL через `UTC_TIMESTAMP(6)` |
| Page cache показывает кнопку «Отложить» у зарезервированной книги | Кнопка получает статус через `GET /catalog/availability` (no-store). Сервер в любом случае отвечает 409 |
| Пользователь открыл корзину — продлился ли резерв? | Нет. `GET /cart` только читает. Продление не предусмотрено, новая попытка возможна только после истечения или удаления |
